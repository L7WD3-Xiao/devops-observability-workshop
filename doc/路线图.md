**从0到“可观测性 + CI/CD + 高可用”**的具体落地路线图

---

## 路线总览（建议5周，可压缩）

| 阶段 | 主题                  | 产出                                    |
| ---- | --------------------- | --------------------------------------- |
| 0    | 脚手架 & 业务雏形     | 一个能跑的短链服务（HTTP + DB + Redis） |
| 1    | **可观测性骨架**      | Metrics + Logs + Tracing 三大信号跑通   |
| 2    | **SLO & 告警**        | 一个核心SLO + 能用的一条告警            |
| 3    | **CI/CD**             | push代码 → 自动构建 → 自动部署          |
| 4    | **高可用 & 容灾模拟** | 能扛住一个单点故障 & 能说明白           |

👉 最核心推荐：**第1、2、3周必须做完**，第4周看时间弹性投入。

---

## 阶段1：短链服务

用来做“载体”，不花过多时间。

### 最小功能

- POST `/shorten`（生成短链）
- GET `/{code}`（跳转原始长链）
- Redis 做缓存（先查redis，miss再查DB）
- MySQL 存储映射

### 技术栈（推荐）

- Go（gin / echo） 或 Java（Spring Boot）
- MySQL + Redis
- docker-compose 本地启动所有依赖

✅ 产出：`curl` 能正常跳转 + 缓存命中

---

## 阶段2：可观测性骨架（最关键，2～3天）

> 目标：不用多漂亮，但三大信号**真实跑通且可关联**

### 2.1 Metrics（Prometheus + Grafana）

- 暴露 `/metrics` 接口
- 埋点：  
  - 请求总数（按 `code`、`cache_hit` 分组）  
  - 请求延迟（Histogram）  
  - 错误数
- Grafana 做 **一个面板**：QPS + P99 + 错误率

### 2.2 Logging（结构化 + Loki）

- JSON 格式日志
- 每条日志包含：`trace_id`、`span_id`、`method`、`latency_ms`
- Loki 采集并在 Grafana 里能检索

### 2.3 Tracing（OpenTelemetry + Jaeger / Tempo）

- 对 HTTP 入口、DB、Redis 进行 tracing
- **关键点**：将 trace_id 注入日志
- 能在 Jaeger 里看到一个完整请求的火焰图

### ✅ 阶段2产出（面试关键素材）

> “我从 Metrics 发现某个短链 P99 飙高 → 点击到 Trace 看到 Redis 耗时异常 → 用 trace_id 查日志确认是缓存击穿”

👉 这已经能赢过 80% 校招 DevOps 项目

## 阶段3：SLO & 告警（1天）

> 校招最稀缺的能力是“用数据做决策”，SLO 是最好的载体

### 3.1 定义一个SLO（不要多）

- 目标：`短链跳转 GET /{code}` 在 100ms 内成功返回
- SLI = 100ms 内成功请求数 / 总请求数
- **错误预算** = 1 - SLO（例如 1%）

### 3.2 SLO 看板 & 告警

- Grafana 展示：当前错误预算剩余百分比
- Prometheus 告警规则：
  - `错误预算消耗过快`（例如 10 分钟内消耗超过 50%）

### ✅ 阶段3 面试金句

“我为核心 API 定义了 SLO = 99% 请求 < 100ms，并用错误预算控制变更风险。有一次压测后错误预算告警，我们暂停发布，优先做缓存优化。”

## 阶段4：CI/CD（1.5～2天）

**重点不是复杂，而是完整闭环**。

### 推荐最简单的方案（对你写简历完全够）

- GitHub + GitHub Actions（或 GitLab CI）
- 流程：
  1. lint & test
  2. build 镜像
  3. push 到 Docker Hub / 阿里云ACR
  4. 在服务器上 `docker compose pull && up -d`

### 你做的最少但完整的事

- 一个 `.github/workflows/deploy.yml`
- **至少区分一次环境**：dev / prod（可以只是改 tag 或 compose 文件）

### ✅ 阶段4 产出

“我实现了从 git push 到 dev 环境自动部署的全流程，并提出过引入 health check 避免流量打到未就绪容器。”

---

## 阶段5：高可用 & 容灾（1天，弹性投入）

**不做真正多机房，但模拟 + 设计思路**

### 5.1 消除单点（设计中体现）

- 短链服务本身 → 可水平扩展
- Redis → 哨兵模式（本地模拟）
- MySQL → 主从（可选，至少能说清楚）

### 5.2 故障模拟（面试最加分）

- 手动停掉 Redis
  - 你的服务是否降级（只查 DB）？
  - 是否有 Metrics 突增告警？
- 手动停掉一个服务实例
  - 负载均衡是否把它摘掉？

### ✅ 阶段5 一句话

“我在设计上消除了单点故障，并实际模拟过 Redis 宕机验证降级逻辑与告警。”

## 这条路线为什么“对中厂校招最友好”

| 面试官会问              | 你对应来自阶段                     |
| ----------------------- | ---------------------------------- |
| 你怎么知道系统出问题了  | 阶段1（Metrics + 告警）            |
| 你怎么定位根因          | 阶段1（trace_id + 日志 + Tracing） |
| 你做没做过容量/质量决策 | 阶段2（SLO）                       |
| 代码怎么上线的          | 阶段3（CI/CD）                     |
| 服务挂了怎么办          | 阶段4（容灾思路 + 模拟）           |

## 最后的现实建议（非常关键）

- **不要求全**
  - 阶段1 + 2 + 3 = **足够中厂一面**
  - 阶段4 = **中厂二面/三面区分度**

- **面试时不要念工具名**
  - ❌ “我用 Prometheus、Grafana、Loki、Tempo、Jenkins”
  - ✅ “当 P99 延迟突然上升，我通过 trace_id 把 metrics、trace、日志串起来，定位到是某条冷短链击穿了缓存”

- **你可以很自信地说**  
  “我没有造可观测性轮子，但我在项目里完整落地了三大信号 + SLO + CI/CD，并模拟了高可用场景。”
